ABSTRACT
Vulnerability assessment and penetration testing (VAPT) is still an expert-driven, largely manual discipline. The tools themselves are mature and scriptable. What stays human is the judgement that sequences them, reads what a result means and keeps track of what has already been ruled out. Large language models look like a good fit for that orchestration layer, but the hosted models strong enough to do the job need target names, banners, credentials and raw tool output sent to a third party, and an engagement contract usually forbids that data from leaving the client.
This project presents CISM (Cyber Investigation State Memory), an autonomous VAPT agent driven by a small language model (SLM) served locally over an OpenAI-compatible endpoint, so no engagement data leaves the operator's machine. The agent is a LangGraph state machine with six nodes: think, act, extract, route, remember and respond. Its main contribution is the dependency and error propagation graph (DEPG). A per-tool extractor turns every successful tool invocation into nodes and edges, each carrying the quoted output that justifies it, so a claim the model cannot ground against real tool text is demoted instead of reported. A tiered, salience-ranked memory survives across turns. A six-phase PTES state machine constrains what may happen next, and a guardrail chain blocks out-of-scope targets, dangerous arguments and phase-illegal tools before any process is spawned. Nine real tools execute only through one sandboxed, argv-only seam behind a hard allowlist, and the operator works in a terminal interface that consumes a frozen event stream, which makes every run recordable and replayable.
CISM was evaluated against a containerized Damn Vulnerable Web Application on an isolated Docker network, driven by a locally hosted llama.cpp server, with the agent running inside the hardened container it ships with. The live runs exposed three extractor defects. Correcting them took one engagement from zero to eight evidence-backed findings across the affected tools. The headless harness reproduced a first finding in about three seconds over repeated runs, and the implementation is covered by 786 automated tests.
Keywords: penetration testing, autonomous agents, small language models, local inference, dependency and error propagation graph, PTES, guardrails, sandboxing.

Chapter 1 Introduction
1.1INTRODUCTION
A penetration test is a structured, authorized and time-boxed attempt to compromise a system the way a real adversary would, so the defects it finds can be fixed before someone less friendly finds them [1]. Vulnerability assessment and penetration testing (VAPT) covers both halves of that work. The assessment half enumerates and classifies weaknesses; the testing half tries to show that a given weakness can actually be exploited. The second half is what makes the first one usable, because a scanner finding nobody has validated is still only a hypothesis.
The individual instruments of the discipline are mature. Port and service discovery, web server scanning, technology fingerprinting, directory brute-forcing, injection testing and credential testing all have well-known, scriptable implementations. The layer above them has not been automated. Someone still has to choose which instrument to reach for given what the last one returned, judge whether a banner is worth pursuing, remember across hours of work that a hypothesis has already been eliminated, and notice when the engagement has moved from reconnaissance into exploitation. That work is judgement, and a human operator does it while holding most of the state in their head and in a scratch file. The defensive side of the same problem is also well studied, including machine-learning detection of SQL injection [2]–[5] and of intrusions more generally [6]–[8].
Large language models suit that layer, because the work is reading semi-structured text, picking an action and justifying it. The obstacle is confidentiality, not capability. The hosted frontier models that orchestrate tools best require target addresses, service banners, discovered credentials and raw tool output to travel to a third-party provider, and that is the material an engagement contract usually keeps inside the client's estate. An offensive-security agent that only runs against a hosted endpoint is therefore unusable for a large share of real engagements, however well it reasons. Language-model agents of this kind now have dedicated surveys [9], and penetration testing has become one of their most active security applications [10]–[16]. Privacy-preserving techniques for language models, such as differentially private text generation [17] and differential privacy for clinical coding [18], address a neighbouring concern: they protect the data a model is trained or prompted with, not the act of sending engagement material to a hosted provider.
This project starts from the other end. CISM (Cyber Investigation State Memory) is an autonomous VAPT agent built around a small language model (SLM) served locally over an OpenAI-compatible endpoint, so inference is an ordinary process on the operator's own machine and no engagement data crosses a network boundary. A small model reasons less reliably than a hosted frontier model, so the system compensates with structure instead of scale. An explicit phase state machine constrains what may happen next. A graph of evidence-backed findings replaces the model's own recollection, a salience-ranked memory survives across turns, and a guardrail chain refuses actions the model should not have proposed. The model supplies direction; the machinery around it supplies memory, grounding and safety.
1.2OVERVIEW OF AUTONOMOUS PENETRATION TESTING
An autonomous penetration-testing agent is a perception-decision-action loop over a security toolchain [19]. It perceives by reading the textual output of a tool it has just run, decides by selecting the next tool and its arguments, and acts by executing that tool against a target inside the agreed scope. It also has to remember, because a finding is usually only visible in combination with an earlier one. An open port on its own is nothing. An open port, plus a version banner, plus a known defect in that version, plus a successful authentication attempt is a finding, and those four observations may be minutes or hours apart.
The engagement itself is conventionally divided into phases. The Penetration Testing Execution Standard (PTES) [20] is the structure adopted in this project, reduced to the six phases the agent actually models: reconnaissance, enumeration, vulnerability discovery, exploitation, post-exploitation, and reporting. Phases earn their place for two independent reasons. They bound the tool set, since a credential-testing tool offered during reconnaissance invites the model to skip straight to intrusive activity. They also give the operator a legible notion of progress, which a free-running agent otherwise lacks entirely.
A realistic engagement does not proceed linearly. Compromising one host frequently restarts reconnaissance against a second host reachable only from the first. A phase model that enforces a strict sequence mis-models the work, while one that permits arbitrary jumps enforces nothing. The design adopted here is an explicit transition table: each phase declares the phases it may legally move to, which makes a realistic pivot expressible and an arbitrary jump impossible.
1.3CHALLENGES IN SLM-DRIVEN PENETRATION TESTING
1.3.1CONTEXT WINDOW AND STATE LOSS
A penetration test generates far more text than a small model can hold. A single full-port service scan can emit over a thousand lines, and a web scanner produces hundreds. A model with a thirty-two-thousand-token context window will have evicted the reconnaissance output long before exploitation begins. Appending every tool result to the conversation therefore guarantees that the agent forgets the evidence for its own conclusions at the moment it needs that evidence. State has to live outside the conversation, in a structure the agent can query [21], and the conversation has to carry references to it instead of raw output.
1.3.2UNGROUNDED FINDINGS
A language model asked to summarize tool output will, under uncertainty, produce a fluent and plausible summary that the output does not support [22]. In a security report that failure mode does unusual damage. A hallucinated vulnerability consumes remediation effort the client pays for, and it discredits the genuine findings beside it. Every claim the agent records must therefore trace back to a literal span of real tool output, and a claim that cannot be traced has to be visibly demoted instead of quietly accepted.
1.3.3SCOPE, SAFETY AND BLAST RADIUS
An agent that can spawn processes with network access and attacker-grade tooling is a liability unless its reach is constrained before execution. Three distinct hazards arise: targets outside the authorized scope, arguments that turn a legitimate tool into an arbitrary file-read or code-execution primitive, and tools invoked at a point in the engagement where they are not yet appropriate. Each one has to be checked against the actual arguments of the call, and each one has to deny by default.
1.3.4AUDITABILITY AND REPRODUCIBILITY
A penetration test is a deliverable, and a deliverable has to be defensible. An operator must be able to say what the agent did, in what order, on what evidence, and why it chose one branch over another. That requirement shapes the architecture as strongly as any functional one. It demands that every externally visible occurrence be an immutable, sequenced record instead of a transient user-interface update, so a run can be stored, replayed, diffed, and quoted in a report.
1.3.5CAPABILITY LIMITS OF SMALL MODELS
A model small enough to run on a single consumer GPU is measurably weaker at tool selection than a hosted frontier model. Two failure modes were observed here: answering a tool-offering turn with a question about information already supplied, and calling a tool with an un-substituted placeholder argument. A design that assumes the model is correct will fail. The design adopted here treats the model as a fallible proposer whose proposals get validated, constrained, grounded and, where possible, recovered from.
1.4PROJECT STATEMENT
To design and implement an autonomous vulnerability assessment and penetration testing agent that is driven by a locally hosted small language model, that keeps all engagement data on the operator's machine, that records every finding as an evidence-backed node in a dependency and error propagation graph instead of as model prose, that constrains its own actions through an explicit phase state machine and a guardrail chain evaluated before execution, that executes every real tool inside a sandbox through a single audited seam, and that presents the whole engagement to the operator through a terminal interface which only consumes a recordable and replayable event stream.
1.5OBJECTIVES
To design an agent architecture in which reasoning, tool execution, finding extraction, phase progression and memory consolidation are separate, independently testable stages of one explicit state machine.
To implement a dependency and error propagation graph (DEPG) that converts raw tool output into typed, evidence-backed nodes and edges, and that derives each node's state from its evidence and the support of its preconditions.
To implement per-tool deterministic extractors for the tools whose output format is stable, with a grounded, structured-output model-based extractor as the fallback for the remainder, demoting a node whenever a claimed quotation is absent from the real output.
To implement a tiered, salience-ranked memory store that survives across turns and collapses recurring observations onto a single row instead of duplicating them.
To implement a six-phase PTES state machine with an explicit legal-transition table, and to gate tool availability on the current phase.
To implement a chain-of-responsibility guardrail evaluated before execution, carrying scope, dangerous-argument and phase-tool stages, with a tool registry that is a hard allowlist.
To execute every real tool through a single sandboxed seam with argv-only invocation, a disposable scratch directory, bubblewrap isolation and a process-tree-killing timeout.
To build a terminal user interface that consumes a frozen, sequenced event stream, so a run can be recorded, replayed and exported without the interface ever calling into the agent.
To validate the system against a live containerized vulnerable target driven by a locally hosted inference server, measuring findings produced, time to first finding, and rendering cost.
1.6SCOPE OF THE PROJECT
The project delivers a working agent, its supporting domain model, its operator interface, a hardened container to run it in, a headless benchmark harness, and a test suite. The following fall within scope:
A LangGraph-backed agent core with six executable nodes and a checkpointer that preserves state across turns within a process.
A catalog of nine real security tools, eight of them declared declaratively and one hand-written, each reachable only through a sandboxed execution seam.
An evidence-backed DEPG with deterministic extractors for the stable-format tools and a grounded model-based fallback for the rest.
A terminal user interface with a scrolling transcript, a one-line adaptive status bar, and two modal views over the graph and the memory store.
Markdown, JSON and SVG report generation from the final graph and memory state.
Validation against a containerized Damn Vulnerable Web Application target on an isolated Docker network, driven by a local llama.cpp server.
The following fall outside the scope of this work and appear as future work in Chapter 6:
Any form of unauthorized testing. The system is a hard allowlist by construction, and it is meant for use only against targets covered by written authorization.
Post-exploitation capability beyond the modelled phase, including persistence, lateral movement implants and privilege-escalation chains.
A web dashboard or any graphical surface. The terminal is the only operator surface by design.
Fine-tuning or training of the underlying language model. The system accepts any OpenAI-compatible server and treats the model as replaceable.
Egress filtering of the sandbox at the network layer, and a formal grammar for tool arguments. The audit identified both, and both are left as future work.

Chapter 2 Background
2.1INTRODUCTION
Chapter 1 named the problems the design has to answer. This chapter supplies the material those answers rest on: the phase standard the agent follows, the published systems it is measured against, what a locally served model can and cannot be relied on to do, the orchestration framework chosen to express it, the graph formalism that holds its findings, and the containment techniques applied to tool execution. It closes with the threat model the system assumes and the gaps Chapter 3 answers.
2.2THE PENETRATION TESTING EXECUTION STANDARD
PTES organizes an engagement into seven sections: pre-engagement interactions, intelligence gathering, threat modelling, vulnerability analysis, exploitation, post-exploitation and reporting [20]. For an autonomous agent the useful part of the standard is its ordering, which encodes the professional convention that intrusive actions follow enumeration, and enumeration follows discovery. An agent that ignores the ordering will, given an ambiguous instruction, reach straight for the most aggressive tool it has.
CISM models six phases: reconnaissance, enumeration, vulnerability discovery, exploitation, post-exploitation and reporting. Each one carries a system prompt telling the model what the phase is for, and the subset of the tool catalog legal in it. The phase is therefore the mechanism that narrows the tool surface available to the model, and not advice the model can ignore.
2.3SURVEY ON MODEL-DRIVEN OFFENSIVE SECURITY AGENTS
Work on applying language models to offensive security falls into three broad groups. The first treats the model as an advisor. The operator runs the tools, and the model interprets output and suggests a next step. This arrangement carries the least risk and the least leverage, since the human stays in every loop [10].
The second group treats the model as an orchestrator with shell access. A prompt loop gets a terminal and a goal, and each command's output feeds back as the next observation. Published systems in this group show that a strong enough hosted model can chain several steps of a simple engagement unaided [11]–[13]. They also share three weaknesses that bear directly on this work. Depending on a hosted frontier model makes them unusable wherever engagement data cannot leave the client estate. Unrestricted shell access leaves the blast radius of a mis-generated command unbounded. And their findings live only as prose in a transcript, so nothing separates an observation the tool output supports from one the model inferred. Later systems extend the pattern to multi-agent coordination with domain-adapted models [14] and to web-application targets [15], [16].
The third group focuses on specific sub-tasks, such as generating an exploit for a known defect, writing a scanner rule, or triaging a crash. This work is largely orthogonal to orchestration. It matters here mainly as evidence that model-generated security artefacts need verification against ground truth before use, which is the conclusion the grounded-extraction design arrives at from the orchestration side. Benchmarks for the underlying capability have appeared alongside these systems, scoring a model against self-contained security tasks instead of a whole engagement [23].
Cutting across those three groups is a question of how much of the engagement the model is trusted to decide. At one extreme the model picks the next command freely from an unrestricted shell. At the other it selects from a fixed menu of parameterized actions. The free-form arrangement looks more capable on paper and is markedly harder to contain, because the set of things a shell can be asked to do is unbounded and cannot be enumerated in advance for checking. The menu arrangement bounds the blast radius at the cost of confining the agent to whatever its author anticipated. This design sits deliberately on the menu side of that line, with the catalog declared as data so widening the menu stays a routine change.
A second difference is where the engagement's state is held. Most published systems hold it in the conversation itself, which couples the agent's memory to the model's context window and loses the oldest evidence first. A smaller number maintain an external store, usually a flat list of observations. Neither arrangement records the dependency between observations, so neither can answer the question an operator actually asks at the end of a test, which is what the conclusions rest on. That question is what motivated the graph structure adopted here.
The common gap across the literature is structural. The agent's beliefs are never separated from its narration. A finding that exists only as a sentence in a transcript cannot be contradicted by later evidence, cannot be pruned when its precondition is disproved, and cannot be cited in a report. Recording findings as a graph with attached evidence, described in section 2.6, answers that gap.
2.4SMALL LANGUAGE MODELS AND LOCAL INFERENCE
A small language model, for this work, is one that runs usefully on a single consumer accelerator: roughly one to eight billion active parameters, quantized [24]. Servers such as llama.cpp's server, vLLM, LM Studio and Ollama expose such models behind an OpenAI-compatible HTTP interface. An agent written against that interface can treat the model as a replaceable component, and can point at a hosted endpoint instead when policy allows it.
Local inference buys confidentiality and costs capability. Three consequences shape the design. Native tool-calling support varies across servers and quantizations, so the agent has to fall back on parsing a structured tool call out of plain text. Context windows are smaller, which pushes state outside the conversation [21]. Instruction-following degrades over long contexts, so the system has to treat a malformed or absent tool call as an expected event.
2.5AGENT ORCHESTRATION FRAMEWORKS
An agent of this kind can be written as a hand-rolled loop interleaving reasoning and action in the prompt [19], as a graph of nodes with typed shared state, or as a set of cooperating agents [9]. The hand-rolled loop is the simplest to start and the hardest to test, because streaming, tool dispatch, state mutation and phase progression all end up interleaved in one function. The multi-agent arrangement adds a coordination problem this task does not have.
This project uses LangGraph, which expresses the agent as a directed graph of nodes over a typed state object, with a checkpointer that persists state between invocations. The property that earns its place is that each node is an ordinary asynchronous function of state. The phase router, the extraction step and the memory consolidation step can each be tested in isolation with a constructed state and no model, no network and no tools. Streaming works at the node level, which lets the interface show narration as it is produced while knowing nothing about the graph.
2.6DEPENDENCY AND ERROR PROPAGATION GRAPHS
A dependency and error propagation graph is a directed graph in which a node is a claim about the target and an edge is a dependency: the claim at the head holds its meaning only while the claim at the tail holds. The formalism comes from fault analysis, where it describes how the failure of a component invalidates everything downstream of it, and it transfers to security assessment with little modification, because a penetration test is largely an exercise in conditional claims. A credential is useful only while the service that accepts it stays reachable. An exploit is relevant only while the version it targets is the version actually deployed. Bayesian networks have been applied to network vulnerability assessment [25], and attack graphs support probabilistic inference about how compromise propagates through a network [26]. Such graphs can be generated automatically from a model of hosts and exploits [27], which applies the same conditional structure at network scale.
Three properties make the structure worth its implementation cost. A claim can be contradicted: when later evidence disproves a node, everything that depended on it is invalidated automatically instead of rotting in a transcript. A claim can be justified, because the evidence attached to a node records which tool produced which text at what time, which is what a report has to cite. And a claim can be deduplicated, since node identity derives from a normalized target and a cause class, so the same finding arriving from two tools collapses onto one node and the finding count stays honest.
2.7SANDBOXING AND GUARDRAILS FOR TOOL-USING AGENTS
Containment for a tool-using agent operates at two levels. The outer level is operating-system isolation of the process the tool runs in: a restricted filesystem view, dropped capabilities, a constrained system-call surface, resource ceilings, and a timeout that kills the whole process tree and not just the leaf. Bubblewrap provides a usable unprivileged implementation of the filesystem and namespace part, and container runtimes supply the rest [28], whose own weaknesses are well documented [29].
The inner level is argument-level policy, evaluated before the process exists. Operating-system isolation cannot tell a scan of an authorized host from a scan of the client's production network, since both are ordinary outbound connections. Only a check against the declared engagement scope can. The two levels complement each other and neither substitutes for the other: the inner one encodes the engagement contract, and the outer one limits the damage when the inner one gets it wrong.
2.8THREAT MODEL AND ETHICAL CONSIDERATIONS
An offensive-security agent is a dual-use artefact, so the design has to say plainly who it is for and what it refuses to do. The system assumes an authorized operator running a test for which written permission exists, against targets enumerated in that permission. Every mechanism in this report follows from that assumption. The engagement scope is an allowlist, so a target nobody authorized is refused by default and not permitted until someone thinks to forbid it. The tool registry is a hard allowlist, so a tool nobody deliberately constructed into the run cannot be reached by name. The phase model withholds intrusive tooling until the engagement has actually progressed. These are not conveniences; each one exists to make the unauthorized action the one that takes deliberate effort.
The design considers three adversaries. The first is the operator's own mistake: a mistyped address, a scope widened and never narrowed again, a tool invoked earlier than intended. The guardrail chain covers this class, because it evaluates the actual arguments of a call before a process exists. The second is the model, treated as an unreliable proposer and not a trusted component. It may propose a target outside scope, an argument that reads a file off the host, or a tool the phase does not permit, and a stage that never consults the model refuses each of those. The third is the target, which has to be treated as hostile input and not a source of truth: tool output is attacker-influenced text, and a model that reads it can be instructed by it. This is indirect prompt injection, demonstrated against deployed model-integrated applications [30] and the subject of a growing body of attack and defence work [31]–[34]. The guardrail seams for that third case exist in the architecture but carry no implemented stages yet, which Chapter 5 records as a limitation and Chapter 6 carries as future work.
Two practical obligations follow for anyone running the system. The engagement scope has to be declared from the authorization document and not from memory, and the credential wordlists the credential-testing tool draws on may hold only lists the operator is permitted to use. The system ships neither on purpose, and the credential tool's arguments select one of two fixed, named lists instead of an arbitrary path, so the tool cannot be redirected into reading host files. Credentials leaked in public code repositories are a documented source of the material such lists contain [35].
2.9SUMMARY OF GAPS IDENTIFIED
Published model-driven offensive agents assume a hosted frontier model, which the confidentiality constraints of most real engagements rule out.
Findings are recorded as transcript prose instead of structured, evidence-backed claims, so they cannot be contradicted, pruned, deduplicated or cited.
Containment is usually a container boundary alone, with no argument-level policy expressing the engagement scope and no denial of dangerous arguments before execution.
Phase progression, where it is modelled at all, is either absent or a strict linear sequence that mis-models realistic pivots.
Runs are not reproducible. Without an immutable event record, an engagement cannot be replayed, diffed or defended after the fact.

3.4SYSTEM ARCHITECTURE
The system has four layers. The interface layer is a terminal application that consumes events and owns no engagement state of its own. The agent layer holds the LangGraph state machine, the phase model, the guardrail chain and the tool registry. The domain layer holds the graph and the memory store, which are plain data structures that know nothing about models or terminals. The execution layer is the sandbox seam and the tools it runs. Dependencies point one way only: the interface depends on the event vocabulary, the agent depends on the domain and execution layers, and the domain layer depends on nothing but the event vocabulary it serializes into.

Figure 3.1   System architecture of CISM
The heaviest decision in this layering is that the interface only consumes. The agent pushes immutable events onto an asynchronous queue, and the application drains that queue and mutates widgets. Nothing in the interface package calls into the agent, and no widget calls a model. A recorded log and a live agent therefore look identical to the interface, which is what makes the demonstration mode, the replay facility and the snapshot tests possible at all.
3.5THE AGENT EXECUTION LOOP
One turn is a cycle through six nodes. The think node binds the tools legal in the current phase and streams a reply; if the model produced tool calls and the per-turn cap has room, control passes to the act node, and otherwise to the respond node. The act node runs each proposed call through the action guardrail chain and then executes it, converting a failure into an observation instead of an exception. The extraction node turns each successful result into graph proposals. The phase router proposes a legal phase move, but only once the graph holds real evidence for the current phase. The memory node folds the step's findings, failures and narration into the memory store, and control returns to the think node.

3.7MODULE DESIGN
3.7.1AGENT CORE
The agent core owns the compiled graph, the checkpointer that keys state to a stable thread identifier, the translation of streamed model output into events, and the operator commands the interface cannot answer by itself. It is the only component that satisfies the agent protocol the interface is written against, which is a queue and four methods: start, submit, interrupt and close.
3.7.2DEPENDENCY AND ERROR PROPAGATION GRAPH
The domain model is a mutable node and edge pair plus a container. The container merges proposals as they arrive, resolves each dirty node's state from its evidence and the support of its preconditions, and prunes regions that are fully disproved. Node identity derives from a normalized target and a cause class, so a host written three different ways collapses onto one node family instead of fragmenting into three.
3.7.3MEMORY STORE
The memory store holds tiered items. Each one carries the phase in which it was seen, a snippet, a hit count and a salience score computed from a tier weight, a time decay and a per-hit bonus. A graph-derived row keys on the node identifier. A narration or failure row keys on a digest of its source, phase and snippet, so a recurring observation increments a counter instead of producing a new row.
3.7.4TOOL CATALOG AND SANDBOX
Eight tools are declared in a catalog file as data, namely binary, capability, target flag, timeout and legal phases. The ninth, the credential-testing tool, is hand-written, because it needs a scratch directory pre-populated with wordlists before the process starts. All nine are assembled into a registry that resolves a name to a bound tool and raises on an unknown name. Every real tool reaches the operating system through one seam, which creates a per-call scratch directory, invokes the binary argv-only under bubblewrap, caps captured output, and enforces a timeout that kills the process tree.
3.7.5GUARDRAIL CHAIN
Guardrails are stages in a chain of responsibility with three seams: input, action and output. The action seam carries the three implemented stages, covering scope, dangerous arguments and phase-tool legality, and short-circuits on the first denial. Adding a check means appending a stage; neither the chain runner nor the graph shape changes.
3.7.6TERMINAL USER INTERFACE
The interface is a single scrolling transcript of per-entry widgets, a fixed composer, and a one-line status bar, with two modal overlays for the graph and the memory store. Styling lives entirely in a stylesheet, and no widget carries inline style. The transcript streams into a buffer the widget owns and refreshes on a coalescing timer, which keeps the per-token cost flat as an entry grows.
3.7.7REPORTING
Report generation walks the final graph and memory state and emits a human-readable Markdown write-up, a structured JSON document for downstream tooling, and a graph diagram. It depends only on the shared event vocabulary and not on the agent package, so a report can be built from an event stream alone.
3.8THE EVENT CONTRACT
Every externally visible occurrence is a frozen record carrying a monotonically increasing sequence number and a wall-clock timestamp. That contract is what makes a run recordable, replayable and diffable, and it is also how secrets stay out of the deliverable. The session-state event carries the name of the environment variable holding the key and a boolean saying whether it is set, and no field anywhere in the vocabulary could hold a key.

4.3THE EXECUTION LOOP IN CODE
The graph is built by a pure factory that wires six nodes and compiles them against a checkpointer. The think node binds the current phase's tool subset to the model and streams the reply. Native tool-calling support varies across local servers, so when the phase offers tools and the model produced none through the native path, the node falls back to parsing a structured tool-call block out of the plain text. The act node is the only place a tool is executed, and it converts every failure into a tool message whose content is the failure text, so the model observes the failure and can react to it instead of the turn ending in an exception.
State persists across turns within a process through the checkpointer, keyed by a stable per-agent thread identifier, so a second instruction sees the graph, the memory and the phase the first one produced. It does not survive a process restart, a deliberate limitation Chapter 6 returns to.
4.4THE INFERENCE CLIENT AND BACKEND ABSTRACTION
The inference client is thin on purpose, because the model is the component most likely to be replaced. A single factory builds a chat model from a base address, a model name and the name of an environment variable holding the key, and returns a canned deterministic model when nothing is configured. The whole system therefore runs, and the whole test suite passes, with no server, no weights and no network. That canned model is not a mock the tests inject. It is the default production path until an operator points the agent at a real endpoint, which keeps the offline path exercised constantly.
Two differences between servers had to be absorbed. Context-window discovery is not standardized across OpenAI-compatible servers, so the client probes where a server exposes the information and falls back to a declared default where it does not; the discovered value is what the status bar's context gauge reports, so an operator sees the real ceiling. Structured extraction is the second difference. A generic function-calling path works on any compliant server, while a raw completion endpoint with a constrained output schema is available for servers that support it, selected by a command-line option. The extraction backend is therefore an interface with two implementations instead of a hard dependency on one wire format.
4.5PHASE STATE MACHINE AND PHASE ROUTING
The phase enumeration and its legal-transition table live in one module, and every transition passes through a single method on the state machine, which gives the rest of the system one choke point to rely on. The phase router advances the phase only once the graph holds real evidence for the current phase. An earlier implementation advanced one phase per successful tool call, which let an engagement reach exploitation on the strength of a scan that found nothing, and the audit corrected it.
Phase legality is enforced twice, on purpose. The phase profile binds only the legal tools to the model, so an illegal tool is normally never offered. A guardrail stage then re-checks the tool against the phase at call time, so a call constructed from a stale binding or from parsed text is still refused.
4.6TOOL CATALOG AND SANDBOXED EXECUTION
Eight tools are rows in a catalog file. A row declares the binary, the capability it provides, the flag that carries the target, a timeout and the phases in which it is legal, so extending the catalog with another flag-and-target-shaped tool is a data change. Its wordlist arguments select one of two fixed, named lists and never an arbitrary path, which stops a compromised model turning a credential tool into a way to read files from the host.

4.8GRAPH CONSTRUCTION AND EXTRACTION
Extraction is the seam through which a tool result becomes graph proposals. Tools whose output format is stable have deterministic extractors that parse their own text directly and assign a deterministic cause class. Every other tool falls back to a grounded model-based extractor, which requests structured output and is clamped to the lowest confidence tier when a quotation it claims is absent from the tool's real output. Failing that, a generic extractor stamps one untested node per call carrying the tool's own name as the cause class.
Three defects in this layer surfaced only when the system ran against a real target, and they are the clearest evidence of why live validation was necessary. The content-discovery extractor matched none of five genuine hits, one of them an exposed installation script, because the real output interleaves a carriage return and terminal escape sequences from a progress indicator, and those defeated a regular expression written against clean sample text. The fingerprinting tool had no extractor at all and degraded to an opaque hash signal. The firewall-detection tool defaulted to a secure scheme and failed outright against a plaintext-only target. All three were fixed, and the regression tests for the fixes were built from the actual captured output instead of idealized samples.
Node identity is computed after normalization. Scheme, port, case and a trailing dot are stripped from the target before it becomes part of the identity, so three spellings of the same host collapse onto one node family. Each new node is linked to the node that led to it, and the container resolves state from evidence and parent support, pruning regions whose preconditions are disproved.
4.9MEMORY
The memory node folds each step's findings, failures, narration and phase changes into the store. A graph-derived row keys on the node identifier, so the row tracks the node. A narration or failure row keys on a digest of its source, phase and snippet, so a recurring message increments a hit counter instead of producing a new row. Salience combines the tier weight, a time decay and a small per-hit bonus, using the same coefficients as the recorded demonstration log, so a live run and a replay decay identically.
4.10THE TERMINAL INTERFACE
The transcript is built from per-entry widgets inside a scrolling container, with the composer and status bar described in section 3.7.6. Two implementation choices are worth recording. An append-only log widget was rejected as the transcript surface, because such a widget cannot host an interactive toggle, which would have ruled out collapsed tool output. The shipped widget instead appends into a buffer it owns and repaints on a coalescing timer, and section 5.4 reports what that costs against the two alternatives.

The status line stays one line at any width. Each field carries a short form and a priority. On overflow the line degrades to short forms worst-priority-first and then drops whole fields, so the model, phase, context gauge and mode always survive. The elision logic is a pure function of segments and an available width, which allows it to be tested directly at every width instead of through a mounted widget.
Two modal overlays expose the domain model. The graph view shows the nodes as a tree and, for a selected node, the decision trail that led to it beside the evidence that supports it, including the margin by which the chosen branch beat the runner-up. 4.11CREDENTIAL REDACTION
The composer feeds three artefacts that outlive the keystroke: the transcript, the history recalled with the arrow keys, and the file written on export. A credential-shaped argument to any command is therefore masked before the turn is echoed, and the command is refused instead of forwarded. Detection is broad on purpose, because a false positive costs one retype while a false negative leaks a key into a deliverable. The endpoint command reports the endpoint, the name of the environment variable holding the key and whether that variable is set, and it never shows, stores or transmits the value.
4.12OPERATIONAL LOGGING AND REPLAY
Operational logging is separate from both the event stream and the graph evidence. Graph steps, tool calls and guardrail decisions are written as structured lines to a log file with a retention policy enforced by both rotation and a sweep at startup. The same log provides the read path that pulls one run's events back out for counterfactual replay, which is how a run recorded during an engagement can be re-examined afterwards without running anything against the target again.
4.13REPORT GENERATION
A report walks the final graph and memory state and emits a Markdown write-up for a human reader and a JSON document for downstream tooling, together with a diagram of the graph rendered to vector form where the rendering binary is available and degrading to the source format where it is not. The generator depends only on the shared event vocabulary, so an interface holding an event stream can produce a report without loading the agent package at all.

4.14TESTING STRATEGY
The test suite is organized as one module per source module, so a failure names the unit that broke and not the feature that noticed. Three properties of the architecture make this practical. Every graph node is an ordinary asynchronous function of a typed state object, so the phase router, the extraction step and the memory step are each tested with a constructed state, no model, no network and no tools. The interface only consumes events, so the whole terminal application is tested by pushing a recorded event sequence at it. And the guardrail chain is a list of independent stages, so each stage is tested against the calls it should refuse without constructing the rest of the system.
Terminal appearance is pinned by snapshot tests that capture the rendered screen as vector output and compare it against a stored image. These only mean something if rendering is deterministic, which it is not by default: a spinner's frame clock, the transcript's follow timer and the composer's cursor blink all leak wall-clock time into a capture. A shared fixture stops all three before any capture, and the replay helper waits for the event queue to drain so a capture never races the pump. One invariant test exists purely because of a bug. Every spinner glyph must occupy exactly one terminal cell and must not be East-Asian-ambiguous, which the original glyph set violated, producing a visible jitter in the animation.
End-to-end tests exercise the paths unit tests cannot reach: a full agent run with a blocked input, a full run with a blocked action, scope and replay commands, a live update stream, a run continued across a simulated process restart through the checkpointer, real invocations of two tools through the assembled registry, and one test that drives the terminal application with a real agent instead of a replayed log. Each of the three extraction defects found in live running gained a regression test built from the actual captured tool output, because an idealized sample is what let the defects through in the first place.
4.15LABORATORY ENVIRONMENT AND CONTAINER HARDENING
Validation uses an isolated Docker bridge network carrying a deliberately vulnerable web application as the target. One network detail cost a full test cycle and is recorded here because it is easy to misdiagnose. On the Docker Desktop and Linux-subsystem configuration used here, the host shell has no route to the containers on a user-defined bridge network at all, while a throwaway container attached to the same network reaches them immediately. An engagement run from the host shell therefore produces empty results against a target that is demonstrably up, which looks identical to the model failing to call a tool unless the route is checked first.
[ IMAGE PLACEHOLDER: attach the laboratory network topology diagram: the isolated bridge network, the vulnerable target container, the agent container, and the inference server outside the network ]
Figure 4.6   Laboratory network topology
The agent itself ships as a container, and the hardening applied to it is part of the contribution and not packaging detail. The container drops all capabilities except the one bubblewrap genuinely requires to create its namespaces, applies a restrictive system-call profile written for that single requirement instead of disabling filtering wholesale, forbids privilege escalation, and applies memory, swap, processor and process-count ceilings, so a runaway or malicious tool invocation is bounded and not merely timed out. The inference key arrives as a read-only mounted file and not an environment variable, because an environment variable is visible at the container layer.
4.16OFFLINE DEMONSTRATION MODE
Because the interface only consumes events, a recorded run looks identical to a live one from where the interface sits. The project exploits this with a demonstration entry point that replays a recorded event log through the same protocol the live agent satisfies, preserving original timing and allowing playback speed to be adjusted. The whole operator surface can therefore be demonstrated, reviewed or screenshotted with no laboratory, no model weights and no network, and the same mechanism provides the deterministic input the terminal snapshot tests are built on. The replay path is the real one, driven by a different producer.

5.8OBSERVED FAILURE MODES
Live running exposed three failure modes. All three appear in full below, including the one whose attempted fix was reverted, because the behaviour of a small model under real conditions is the central risk this project set out to manage.
5.8.1A TOOL-OFFERING TURN ANSWERED WITH A QUESTION
The model intermittently answers a turn that offers tools by asking for information it already has, for example requesting the target address when that address sits in both the instruction and the system prompt. The behaviour is non-deterministic: the same model, prompt and target produced a clean five-tool-call run and this failure side by side. A bounded retry on a turn that produced no tool calls was implemented and then reverted. The streaming translation in the agent core forwards every token from any streamed call made inside the think node straight to the event bus, so a discarded first attempt's text leaks into visible narration and double-counts tokens. Six tests that assert exactly one narration and token sequence per turn caught it. A correct fix requires the streaming translation to know that an attempt is discardable, which is a change to the core and not to the node, so it is carried as future work.
5.8.2A PLACEHOLDER PASSED AS A REAL ARGUMENT
The same model separately invoked the port scanner with the literal placeholder token as the target argument instead of the address, producing a real tool call that failed at name resolution. This failure has a different shape from the previous one, in that the model does call the tool but with a templated-looking argument, so no shared cause or fix has been assumed. The likely remedy is an argument-level validation stage in the guardrail chain, rejecting an argument that matches a placeholder pattern before execution.
5.8.3SILENT UNAVAILABILITY UNDER A STALLED PHASE
When an early turn's tool call produces no usable finding, through either of the failures above, the phase never advances past reconnaissance. A later instruction that explicitly requests an injection-testing tool, which the catalog offers only from vulnerability discovery onward, therefore cannot be satisfied. The model substituted other reconnaissance-phase tools instead of calling the requested tool or explaining why it could not, and the operator received no signal that the requested tool was unavailable. This is the most operationally significant of the three, because the agent looks like it is working while silently not doing what was asked. The fix is a visible signal that the current phase does not offer the requested tool.
5.9DISCUSSION
The results support three conclusions. The structural compensations work: grounding every node in quoted tool output, deduplicating identity after normalization, and gating tools on phase together produce a usable engagement from a model that is individually unreliable at tool selection. The failure modes that remain belong to the model's tool-calling discipline and not to the surrounding architecture, and each one has an identified, bounded remedy inside the existing seams. The most practical conclusion is that offline validation against clean sample output is insufficient for this class of system. The three extraction defects that cost eight findings were each invisible to a passing test suite and visible within a single live run.
5.10LIMITATIONS
The input and output guardrail seams exist but pass everything through; only the action seam carries implemented stages.
The dangerous-argument stage is a denylist and not an allowlist grammar, so an argument form nobody anticipated is permitted by default.
Node generality and downstream counts are defined on every node but not yet computed, so graded propagation along weighted edges is inert and a precondition counts as live or dead with nothing in between.
Checkpointed state does not survive a process restart.
Extraction for tools without a deterministic extractor requires a second model round trip, which sits on the critical path of the turn.
Evaluation used a single target application and a single model family, so the results should not be generalized to other targets or models without repetition.
Chapter 6 Conclusion and Future Work
6.1CONCLUSION
This project set out to establish whether a locally hosted small language model can drive a vulnerability assessment and penetration testing engagement end to end without the engagement data leaving the operator's machine, and what has to surround such a model for the answer to be yes. The answer this work supports is a qualified one. The model can supply direction, but only when memory, grounding, phase discipline and pre-execution policy come from the system around it instead of from the model itself.
The system delivered is complete in the sense that counts here: it runs real tools against a real target through a real inference server, and it produces a defensible deliverable at the end. Nine tools execute through one sandboxed, argv-only seam behind a registry that is a hard allowlist and a guardrail chain that refuses an out-of-scope target, a dangerous argument or a phase-illegal tool before any process exists. Findings are not model prose. Each one is a node in a dependency and error propagation graph carrying the quoted tool output that justifies it, with identity computed after normalization so duplicates collapse, and state derived from evidence so a disproved precondition invalidates what depended on it. The operator surface never calls into the agent, which is what makes every run recordable, replayable and exportable. The implementation is covered by 786 automated tests.
The evaluation produced one result the project did not expect to emphasize. Three extraction defects, each of which passed a full test suite written against clean sample output, were exposed within a single engagement against a live target: a progress indicator's escape sequences defeating a pattern, a tool with no extractor at all, and a scheme assumption that was wrong for a plaintext target. Correcting them took one engagement's findings from zero to eight across those three tools, with no change to the model, the target or the instructions. For a system whose purpose is to convert raw tool output into trustworthy claims, validation against real output is the only step that tests the thing that actually matters.
The project also records what it did not achieve. The model's tool-calling discipline remains the weakest component. It intermittently answers a tool-offering turn with a question about information it already has, and it has been observed passing an un-substituted placeholder as a real argument. One attempted remedy was implemented and then deliberately reverted, because the streaming path would have leaked a discarded attempt's tokens into the operator's transcript, a correctness regression that six tests caught. Reporting this is more useful than reporting a clean sweep, because the shape of the failure is what the next phase of work has to address.
6.2FUTURE WORK
The items below are ordered by the leverage they would add, and each one has an identified seam to extend into instead of requiring a redesign.
Make a discarded model attempt invisible to the event stream, so a bounded retry on a turn with no tool calls becomes safe to ship. This is a change to the streaming translation in the agent core, and it unblocks the most common live failure mode.
Add an argument-validation guardrail stage that rejects placeholder-shaped and templated arguments before execution, catching the second observed failure mode where it is cheapest to catch.
Emit a visible signal when the current phase does not offer a tool the operator has explicitly requested, so silent substitution becomes impossible.
Replace the dangerous-argument denylist with an allowlist grammar per tool, so an unanticipated argument form is refused by default.
Implement network egress control for the sandbox, so a tool cannot reach anything beyond the declared scope even when an argument-level check is bypassed.
Compute node generality and downstream counts and activate graded propagation along weighted edges, so a weakened precondition softens its dependents instead of only a disproved one killing them.
Implement the input and output guardrail seams, in particular against content injected through tool output to poison the graph or the memory store.
Persist checkpointed state across process restarts, so an engagement spanning several sessions keeps its graph, memory and phase.
Move extraction for tools without a deterministic extractor off the critical path, so a second model round trip no longer delays the turn.
Broaden the evaluation to additional target applications and model families, repeating the headless benchmark across them to establish how far the present results generalize.

Appendix 3REPRODUCING THE LABORATORY ENVIRONMENT
The laboratory is reproduced by creating an isolated bridge network, attaching the vulnerable target container to it, initializing the target's database once, confirming the target's address on that network and declaring it as the engagement scope, then running the agent from inside a container attached to the same network. That last step is not optional on the configuration used here. The host shell has no route to the containers on a user-defined bridge network, so an engagement run from the host produces empty results against a target that is up. Confirm the route from a throwaway container on the same network before reading any empty result as an agent failure.
docker network create --subnet 172.28.0.0/24 cism-lab
docker run -d --name dvwa --network cism-lab \
    vulnerables/web-dvwa
docker run --rm --network cism-lab curlimages/curl \
    -s -o /dev/null -w 'HTTP %{http_code}' http://<target-ip>/
docker build -t cism-runner -f cism-runner.Dockerfile .
docker run --rm -it --network cism-lab \
    --cap-drop=ALL --cap-add=SYS_ADMIN \
    --security-opt seccomp=docker/seccomp-bwrap.json \
    --security-opt no-new-privileges \
    --security-opt systempaths=unconfined \
    --memory=2g --memory-swap=2g --cpus=2 \
    --pids-limit=512 \
    -v /tmp/cism_api_key:/run/secrets/cism_api_key:ro \
    cism-runner --live-tools --target <target-ip> \
    --scope <target-ip>/32 --model <model-name> \
    --base-url http://<server>:<port>/v1 \
    --key-file /run/secrets/cism_api_key
Appendix 4DOMAIN MODEL REFERENCE
The two structures that carry the agent's beliefs appear below, since the report refers to their fields throughout.
Table A.3   Fields of a graph node
Field
Meaning
identifier
Derived from the normalized target and the cause class; two proposals with the same identifier merge into one
target
The host, service or resource the claim is about, after scheme, port, case and trailing-dot normalization
cause class
What kind of claim this is; deterministic for a tool with its own extractor, the tool's own name for the generic fallback
state
Derived, never set directly: computed from the node's evidence and the support of its preconditions
evidence
The observations supporting the claim, each naming the tool, the quoted output, the exit status and a timestamp
tier
Confidence tier; clamped to the lowest tier when a claimed quotation is absent from the real tool output
generality
Defined but not yet computed; intended to weight how broadly the claim applies
downstream
Defined but not yet computed; intended to count the claims that depend on this one
Table A.4   Fields of a memory item
Field
Meaning
key
The node identifier for a graph-derived row, or a digest of source, phase and snippet for a narration or failure row
tier
T1, T2 or T3, carrying the weight used in the salience computation
phase
The phase in which the observation was made
snippet
The retained text of the observation
hits
Incremented when an identical observation recurs, instead of adding a second row
salience
Computed from the tier weight, a time decay and a per-hit bonus, using the same coefficients as the recorded demonstration log

Appendix 6PHASE TRANSITION TABLE
Phase legality is declared once, in the table below. A transition the table does not list is refused by the state machine, and every phase may legally stay where it is.
Table A.6   Legal phase transitions
Current phase
May move to
Reconnaissance
Reconnaissance, enumeration
Enumeration
Enumeration, vulnerability discovery, reconnaissance
Vulnerability discovery
Vulnerability discovery, exploitation, enumeration
Exploitation
Exploitation, post-exploitation, vulnerability discovery
Post-exploitation
Post-exploitation, reporting, reconnaissance
Reporting
Reporting

Two entries carry most of the design intent. Enumeration may fall back to reconnaissance, which is what a newly discovered host on an adjacent segment requires, and post-exploitation may return to reconnaissance, which is the pivot a compromised host makes possible. Reporting is terminal: once an engagement is being written up, the agent cannot silently resume testing.
