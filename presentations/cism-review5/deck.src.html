The problem

A 96k window still fills inside one engagement.

The server reports a window of 98304 tokens. The agent reads that number at startup rather than assuming one, so the budget is the real window.

One engagement reached 76014 tokens. That is past 0.75 of the budget, which is where compaction starts working whether or not anything has overflowed yet.

Headroom is not the answer. A three hour engagement will spend whatever window it is given.

Motivation

Why a small model on a 6 GB laptop.

Three constraints pick the design. None of them is a preference.

RTX 30506 GB laptop GPU
24 GBsystem RAM
90calls per model
  1. Constraint 01 The engagement data cannot leave the building. A hosted model strong enough for this work needs target names, banners, credentials and raw tool output sent to a third party. The contract usually forbids exactly that, so the model has to run on the operator's own machine.
  2. Constraint 02 The machine is a laptop, not a cluster. The driver has to fit a 6 GB consumer GPU alongside Windows. Nothing much above 9B runs at a usable speed there. The model will be weak at exactly the judgement this task needs.
  3. The turn The obvious fix is the wrong one. A security tuned model looks like the answer. We tested that directly: every community cybersecurity fine-tune except one full merge got worse at calling tools than the model it was built from. Domain knowledge belongs in the agent's tools, not in the weights.
cism / 02

Walk the three in order. The first two are givens. The third is the one the panel has not heard: we tested the obvious move and it lost. That failure is what justifies spending the project on the architecture around the model instead of on picking a cleverer model.

The agent loop

Six nodes, one loop, one budget check.

Click any node.

The agent is a LangGraph state machine with six nodes: think, act, extract, route, remember and respond.

State persists across submissions within one process through a checkpointer.

think

The only node that talks to the model. History is compacted against the context budget here, before the call is made.

The findings summary injected alongside it is rebuilt fresh every think() call from graph state rather than chat history.

act

Each proposed call runs the action guardrail chain first. The tool executes only if every stage allows it.

At most 2 model turns run per user turn.

depg_update

Successful tool results become graph nodes and edges through a per tool extractor, each carrying the quoted output that justifies it.

phase_router

Proposes the next phase. The state machine accepts it only if the transition table allows it.

memory_update

This step's findings, failures, narration and phase changes upsert into the tiered memory store.

respond

The output guardrail runs on the final text, then the run ends.

The budget

No generic local tokenizer exists, so the estimate is 3 characters per token with 4 tokens of overhead per message. 512 tokens stay reserved for the answer.

The window

The default window is 32768 tokens. The system prompt is subtracted first, because it is sent on every turn.

The cascade

Each tier runs only when the one before it still did not fit. Full history stays in state. This only shapes what is sent to the model.

Phase lock

An illegal phase jump is not reachable.

Six phases, one choke point.

Every phase change goes through PhaseStateMachine.transition(). Nothing else may move the phase.

Dashed arcs are the legal pivots back. Reporting accepts only itself.

recon

Guardrails

Nothing spawns before every stage allows it.

  1. 01ScopeGuardStageBlocks a call whose target falls outside the declared engagement scope, a CIDR and domain allowlist.
  2. 02DangerousFlagGuardStageBlocks free form flags that could read or write outside the scratch directory, or trigger code execution.
  3. 03PhaseToolGuardStageRe-checks the tool against the current phase allowlist at call time, not at registration time.
  4. 04ToolOutputScreenStageScreens tool output for prompt injection markers before it is fed back into the model.
  5. 05OutputRedactionStageRedacts credentials and secrets from the final answer the operator sees and exports.

The catalog fails closed. A tool that writes, executes or destroys is registered but unreachable in every phase until someone adds an explicit phases key.

cism / 08

This is the ethics and safety answer. The chain runs before any process exists. Say plainly that these are heuristic safety nets rather than formal guarantees. The fail closed catalog default is the part we are most confident in.

Containment

Execution is argv only. A quoted string never reaches an interpreter.
No persistence

No orphans

hydra's wordlist arguments only ever select one of two fixed, named wordlists.

Defence in depth. The guardrails decide whether a call happens. This seam decides what a call can touch once it does. The key arrives as a read only mounted file, never as an environment variable.

cism / 10

Section break into the contribution. This sentence is the design rule the next two slides implement.

Dependency and error propagation graph

Every finding carries the output that proves it.

Click any node.

Each edge carries a weight, the propagation coefficient. Each node carries r, its reachability.

The graph merges proposed nodes, resolves each dirty node, then prunes fully dead regions.

Identity before merge

Targets are normalized before they become part of a node's identity, so 10.0.0.5, ssh://10.0.0.5:22 and 10.0.0.5. collapse onto one node family instead of fragmenting.

Where r comes from

Evidence tier sets the starting score: T1 is 1.0, T2 is 0.8, T3 is 0.5. A tier the model chose rather than a parser is discounted by 0.85, which is why this node sits at 0.85 and not 1.00.

Weights weaken, they do not kill

This node reaches 0.80 because the edge from its parent carries a weight of 0.8. A weak precondition softens its children instead of either passing them through untouched or killing them.

Disproved is absolute

Dead evidence sets the score to 0 regardless of parents. Anything downstream loses that term of the noisy OR entirely.

Below the line

At 0.43 this node is neither resolved nor blocked. It is contested, and it stays in the operator's view as unproven rather than being reported as a finding.

r = s₀ · (1 − ∏(1 − w·rᵥ)) ≥ 0.6 resolved
≤ 0.15 blocked
cism / 11

The core contribution. Click exposed-dir to explain the 0.85 discount, then ssh-service for the edge weight, then weak-creds for the dead term. The formula at the bottom is the noisy OR. A node needs any live precondition. A weak one only gets it part of the way there.

Tiered memory

Memory decays unless the run keeps hitting it.

Each item carries a tier, the phase it was seen in, a snippet and a salience score.

A recurring narration or tool failure collapses onto one row and increments its hit count instead of filling the view.

Tier weight sets the starting height. The hit bonus is what lifts a row back up.

S = w_tier · s₀ · e^(−λ·age) + β·hits
cism / 12

The equation is live in the terminal memory view, with the current term values substituted per row. Point at the T1 curve and say that an exploited finding stays retrievable far longer than a routine banner.

Observed failure modes

The model lies about its own evidence.

  1. Failure 01It reported a success that the response body flatly contradicts The injection never reached the SQL parser. The body came back byte for byte as the normal result: First name: admin. The narration said the attack was successful and confirmed the database version, then planned the next step on that premise. A checkable claim, false against text its own call already had in front of it.
  2. Failure 02It forgot a correction it had just been given The same encoding mistake came back across four separate turns. The correct form sat in its own immediately preceding successful call. Not a knowledge gap. The right answer was already in the context window.
  3. Failure 03Corrected once, it over-generalized Told to use a literal separator instead of encoding it, it stopped escaping anything at all, and curl rejected the URL outright. A narrow correction became a broad rule. The guardrail caught the result, not the reasoning.

Neither model found or exploited an actual SQL injection in its observed window. We are reporting that, because it is the result.

Limits and next phase

Every limit names the seam it extends into.

What the work does not claim

  • Evaluation covered two targets on one application. It does not generalize to other applications.
  • No confirmed SQL injection exploit landed in either model's observed window.
  • Checkpointed state does not survive a process restart.
  • The sandbox shares the host network, so scope is enforced on argument text and not at the operating system boundary.

Future work, highest impact first

  • Make a discarded model attempt invisible to the event stream.
  • Add an argument validation guardrail stage.
  • Replace the denylist with an allowlist grammar per tool.
  • Implement network egress control for the sandbox.
